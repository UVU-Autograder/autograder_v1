Category Risk Level Detail Mitigation
Security
Execution Malicious student code — reverse shell, fork bomb, privilege escalation Critical Student submits code that opens a reverse shell, spawns unlimited child processes, or attempts to write outside its container. Applies regardless of execution engine choice. --network none at container level. Hard CPU + memory limits via cgroups. Kill entire container on timeout — not just the process inside it. Run as unprivileged non-root user. AST pre-check blocks socket, subprocess, os.system before execution.
Execution Student code reads other students' submissions Critical If containers share a volume or the host filesystem is mounted, one submission could read files from another student's grading directory. Ephemeral per-submission containers only. No shared volumes between grading jobs. Each container receives exactly its own submission via isolated temp directory. Container destroyed immediately after grading completes.
Ingestion ZIP path traversal attack High A crafted ZIP can contain members with paths like ../../etc/passwd that escape the extraction directory when unpacked naively. Instructor or TA uploading a malicious ZIP — even accidentally — could overwrite server files. Validate all member paths before any extraction. Reject any member whose resolved absolute path escapes the target directory. Use Python zipfile with explicit sanitization — never shell out to unzip.
Ingestion Malicious code injected via rubric or constraint upload Medium If rubric/constraint definitions are parsed as executable content rather than plain text, a crafted upload could inject into the grading pipeline. Rubrics and constraints parsed as structured text/JSON only. Never eval'd or exec'd. Schema validation on all uploaded config files before use.
Compliance
FERPA Student code sent to external LLM API Resolved by design Sending student submission code to OpenAI, Anthropic, or any third-party API would require a university-signed Data Processing Agreement and legal review. All inference runs locally on the on-prem Mac Mini via llama-server. No student data transits any third-party infrastructure at any point in the pipeline.
FERPA Grade data released without human review High If AI-generated grades are surfaced to students without TA/instructor sign-off, erroneous grades attach real academic consequences before anyone can catch them. Enforced status machine: ai_complete → ta_reviewed → approved → released. No export path exists until status reaches approved. TA approval is a required DB field — not a UI suggestion.
Audit No audit trail for grade decisions High If a student appeals a grade and there is no record of what the AI produced vs what the TA changed, the institution cannot defend the grade or demonstrate fair process. Immutable audit log stores: AI raw output, per-criterion scores, TA override (if any), final approved grade, approving user ID, and timestamp. Append-only — no record can be edited or deleted.
Resource — Hardware (256GB constraint)
Memory LLM + concurrent grading containers exhaust 256GB Medium On a 256GB machine: Llama 3.3 70B Q4_K_M = ~40GB. OS + stack = ~12GB. Each grading container = ~256MB. At 8 parallel jobs = ~2GB. Headroom is ~202GB — comfortable, but KV cache per active LLM session (~7.5GB each) limits simultaneous inference sessions to ~26 before pressure. Limit Celery to 8 concurrent grading workers. Limit llama-server --parallel to 8 slots. This keeps total memory well within 256GB budget. Monitor with vm_stat and alert if memory pressure reaches warning threshold. Revisit limits if/when 512GB hardware arrives.
Memory Large submission batch causes memory spike Medium An instructor uploads a ZIP of 200 submissions simultaneously. All 200 jobs enter the Celery queue at once. If workers start too many containers in parallel, memory pressure compounds quickly on 256GB hardware. Celery concurrency hard cap of 8. Job queue naturally throttles — jobs sit in Redis until a worker slot is free. No mechanism allows all 200 to execute simultaneously. This is correct behavior by design.
Throughput Grading throughput slower on 256GB vs 512GB Low 256GB Mac Mini M3 generates ~15–20 tok/s on Llama 3.3 70B Q4_K_M vs ~25 tok/s on M3 Ultra. At 8 parallel slots, a 200-submission batch takes approximately 25–35 minutes vs 15–20 minutes on larger hardware. Acceptable for batch grading — instructors don't wait at the screen. Set expectations: grading runs are background jobs. Consider Gemma 3 27B Q4_K_M (~18GB, faster tok/s) as an alternative model for speed-constrained deployments.
Continuity Single point of failure — one on-prem machine Medium If the Mac Mini goes offline (power, hardware failure, macOS update reboot), all grading, the web app, and the database become unavailable simultaneously. Enable macOS auto-restart after power failure. Use launchd service files for llama-server, FastAPI, Redis, and Celery — all restart automatically on reboot. PostgreSQL data directory on separate volume or Time Machine backup. Document manual recovery procedure. Evaluate second machine for M2.
Application
LLM AI feedback contradicts actual test results High LLM generates a comment saying "your loop logic is correct" for a submission where the loop test failed. Student receives conflicting signals — erodes trust in the system. Prompt architecture enforces: test result is ground truth, LLM only explains it. Prompt explicitly states the test FAILED and asks only for a pedagogical explanation. LLM is never asked to re-evaluate correctness. Validate with 50 representative submissions before M1 launch.
LLM Infinite loop / fork bomb hangs grading worker High Student submits while True: pass or os.fork() in a loop. Without a hard container-level timeout, this hangs a Celery worker indefinitely, blocking all subsequent jobs in the queue. 10-second hard timeout enforced at the Docker container level — not just pytest. docker run --rm --timeout 10. Container killed entirely after timeout. Job marked failed:timeout in queue. Worker immediately available for next job.
Storage TEXT blob growth in PostgreSQL Low 200 students × 10 assignments × 5 attempts × ~300 lines of Python = manageable for M1 but grows unbounded over multiple semesters without a retention policy. TEXT blobs are correct for M1. Plan volume/object storage migration at M2. Add end-of-semester archiving job that compresses and moves old submissions out of the primary DB.
