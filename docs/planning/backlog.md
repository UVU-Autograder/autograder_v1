### Recommended grading reliability and instructor workflow

These recommendations come from the [autograding platform research](../research/autograding-platforms.md). They retain Canvas grade ownership, the approved Judge0/Kata boundary, local sandbox-only AI and existing student-data expiry. Prioritize failure classification, package validation, admission snapshots, the pinned runtime and focused calibration. The supervisor work is a bounded feasibility experiment before any execution redesign. API/config changes must use the [documented snapshot generators](../running.md#additional-checks).

- [ ] **Accurate execution failure categories:** Replace coarse timeout reporting with evidence-based categories for student syntax/import errors, assertion failures, runtime crashes, confirmed limits, collection/harness defects, invalid result protocols and engine/cleanup failures. Use an unknown execution failure when evidence cannot establish the cause; align backend, browser and exported feedback. **Reason:** Students need actionable diagnoses, staff need to distinguish grader defects from student mistakes, and infrastructure failures must not be presented as earned zeros. Reuse existing engine status evidence before adding new instrumentation.
- [ ] **Required grading assets and path validation:** Validate all required tests/support files before admission or calibration; reject missing/unreadable assets and ambiguous destination collisions rather than continuing with a reduced suite. Define legitimate starter/support overlaps and separate instructor and student path ownership. **Reason:** A partial package can produce plausible but incorrect grades. Explicit validation catches the problem early without replacing the execution engine.
- [ ] **Strict result validation and expected-test inventory:** Introduce a bounded, versioned data-only result envelope with validated fields, allowed outcomes and finite numeric values. Stage in a trusted expected-case inventory, checking duplicate/missing IDs, scoring-key mappings, declared completion and setup/teardown evidence; represent intentional optional/skipped cases explicitly. Preserve existing all-of scoring. **Reason:** Malformed or incomplete reports must not earn publishable credit. Dynamic-test compatibility and protocol migration need explicit handling; structural validation alone does not authenticate results from an interpreter shared with student code.
- [ ] **Complete grading snapshot before dispatch:** Capture config, effective concepts, required grading/support bytes, feedback metadata and runtime/protocol identity before an official run becomes dispatchable. Use atomic writes and coherent recovery across files/database records; queued runs retain their admitted package despite later edits. Verify interruption between package capture and dispatch readiness. Connect to immutable master-course releases when that existing item is implemented, without waiting for full release management. **Reason:** Queue delay must not change the grading rules for a batch. The additional snapshot/recovery complexity is justified by reproducibility; run-specific copies still expire with the run.
- [ ] **Trusted-supervisor feasibility experiment:** Use synthetic I/O, class/function and Pygame assignments to test a supervisor separated from restricted student execution inside the approved VM boundary. Verify enforced permissions protect report state, grading assets and credentials; preserve course semantics and avoid host imports or unsafe object deserialization. Record limitations, compatibility cost and a go/no-go decision before implementation beyond the prototype. **Reason:** Kata host isolation and strict JSON validation do not make a shared student/pytest interpreter a trustworthy result producer. This is a significant design investment, so prove the boundary and teaching compatibility first.
- [ ] **Bounded diagnostics and separate result transport:** Cap student stdout/stderr and assertion diagnostics with visible truncation; give machine results their own size allowance and framing/channel so runaway prints cannot displace the report. Test Unicode, invalid encoding and runaway output. Coordinate with result validation and the supervisor experiment. **Reason:** Unbounded capture wastes resources and can destroy useful grading evidence. Separate framing improves reliability but is not an integrity boundary unless student access is actually restricted.
- [ ] **Explicit intake selection and valid-result export gates:** Surface unmatched entries, normalized-path collisions and multiple candidate submission versions; require a resolved transient source selection instead of silently treating the largest file as authoritative or combining versions. Require valid terminal automated outcomes, required manual completion and resolved intake ambiguity for included exports; offer retry or explicit staff adjudication for infrastructure/harness/protocol failures. Verify preview, CSV and HTML agree. **Reason:** Reliable tests cannot correct grading the wrong files, and completed processing does not necessarily mean a valid grade. Keep candidate data and adjudication detail transient; retain manual Canvas import/distribution.
- [ ] **Clear deterministic feedback and instructor hints:** Explain the failed requirement, available evidence and a permitted debugging step before raw diagnostics. Add optional instructor-authored hints keyed to scoring requirements and reuse them in browser/exported feedback; distinguish concept warnings and pending manual credit. **Reason:** Clear evidence-based feedback helps even when AI is unavailable and adds no external service dependency. Hints should guide without supplying solutions; AI remains explanation-only under the existing sanitized public-input contract.
- [ ] **Manual-review stale-save protection:** Add a client-supplied revision to transient review records, enforce conflicts on the server and provide a clear UI reconciliation path. Retain existing locks/atomic writes and IA/course authorization. Verify that two reviewers cannot silently overwrite one another's edits. **Reason:** File locking prevents write corruption but does not prevent a later save from a stale browser view. The modest API/UI conflict-handling cost is justified by protecting scores and feedback.
- [ ] **Reusable instructor rubric comments:** Start with instructor-authored generic comment templates tied to rubric criteria, with one explicit authority for scores. Keep selected comments and student-specific text within the expiring run; never automatically persist a student's feedback as a template. **Reason:** Repeated marking becomes faster and more consistent without introducing independent annotation arithmetic. Defer source-line anchors and reviewer-claim workflows until observed review needs justify their additional model/UI complexity.
- [ ] **Small aggregate phase and cleanup telemetry:** Measure queue wait, preparation, execution, parsing/scoring and disposal using existing operational mechanisms; surface repeated infrastructure failures and overdue cleanup. Persist only bounded operational aggregates, with detailed timelines confined to transient workspaces and no student/run identifiers, filenames, code or raw feedback as long-lived labels. **Reason:** Phase evidence identifies actual bottlenecks and cleanup failures before capacity changes. Keep instrumentation small to limit upkeep, storage and privacy risk; a new monitoring service is not required by this item.

### Conditional refinements after the reliability work

These remain scoped recommendations, with instructor demand or feasibility evidence required before implementation; they do not authorize broader platform or data-policy changes.

- [ ] **Instructor-requested comparison modes:** Add exact-text or numeric-tolerance helpers only for assignments that need them; preserve current normalized comparison as the compatibility default and preview modes against calibrated cases. **Reason:** Accidental whitespace or numeric assumptions can reject valid work or accept incorrect output. Restrict the option set to demonstrated needs to avoid configuration sprawl and ongoing authoring/test overhead.
- [ ] **Consistent feedback visibility, if private details are requested:** First establish whether an instructor needs different public/official feedback. If so, define execution selection and feedback-detail visibility separately and use one server projection across API, HTML, downloads and AI input, with leak checks. Test-source secrecy requires a demonstrated isolation boundary from the supervisor experiment. **Reason:** UI-only hiding can expose the same detail through another output path. A shared projection reduces inconsistency, but multi-surface policy maintenance is justified only by a concrete teaching requirement.
- [ ] **Optional public local test bundles:** Pilot a generated public pytest bundle for an instructor-requested assignment, with matching release/runtime metadata and no solutions or private tests. Verify local/server public checks agree under the documented environment and assess student setup/support effort before expansion. **Reason:** Local checks may shorten feedback cycles and reduce queue pressure for students comfortable with Python. Environment drift and support burden make this optional; server grading and manual criteria remain authoritative.
- [ ] **Selective package-import feasibility:** Evaluate a named supported subset of an upstream package format only when a real instructor package would benefit. Compare conversion with direct authoring; require explicit warnings/rejections and score-parity checks before adopting an adapter. **Reason:** Reuse can reduce duplicate authoring, but external format changes create maintenance obligations. Do not accept arbitrary plugins/images or build a general importer without evidence of worthwhile savings.
