# PrairieLearn: reproducible content and grader contracts

Inspected 2026-10-06 from a shallow clone of [PrairieLearn/PrairieLearn](https://github.com/PrairieLearn/PrairieLearn), commit `3d750c422e29a444b22d77bbe9e94fece7ea89e6` (commit timestamp 2026-10-06). Source inspection only; no application or external grader was run. The clone was removed before cloning Autolab. [Comparison and integration proposal](autograding-platforms.md).

## Architecture and execution model

PrairieLearn is an assessment platform whose questions can generate, parse, grade and test themselves. Its current repository is a TypeScript monorepo with a principal application, a separate grader-host application, Python question/grader support, PostgreSQL schema definitions and example/test courses. Questions and assessments are distinct: content definitions are reused across course instances, while assessment policy determines attempts, scoring and access. [Repository introduction](https://github.com/PrairieLearn/PrairieLearn/blob/3d750c422e29a444b22d77bbe9e94fece7ea89e6/README.md), [question execution](https://github.com/PrairieLearn/PrairieLearn/blob/3d750c422e29a444b22d77bbe9e94fece7ea89e6/apps/prairielearn/src/question-servers/freeform.ts).

The question lifecycle has explicit `generate`, `prepare`, `render`, `parse`, `grade` and `test` phases. A variant records a seed, generated parameters and answers. The authoring documentation explains how seeded random generators reproduce variants and warns that displayed rounding must agree with grading calculations. Its `test()` contract generates correct, incorrect and invalid inputs and compares the expected parse/grade results with actual behavior. This tests the grader, not merely the student's solution. [Lifecycle, randomization and question testing](https://github.com/PrairieLearn/PrairieLearn/blob/3d750c422e29a444b22d77bbe9e94fece7ea89e6/docs/question/server.md), [variant table](https://github.com/PrairieLearn/PrairieLearn/blob/3d750c422e29a444b22d77bbe9e94fece7ea89e6/database/tables/variants.pg).

External grading has a filesystem protocol. The platform assembles selected course files, question tests, student files and a JSON data object into different directories. The chosen grading image/entrypoint writes `results.json`; the result processor handles malformed output, validates required fields and translates it into application grading state. Local development uses a Docker execution implementation; the production-oriented grader host includes queue receipt and visibility-extension logic. This distinction matters: a local container configuration does not describe the complete production job lifecycle. [External grading documentation](https://github.com/PrairieLearn/PrairieLearn/blob/3d750c422e29a444b22d77bbe9e94fece7ea89e6/docs/externalGrading.md), [payload builder/result conversion](https://github.com/PrairieLearn/PrairieLearn/blob/3d750c422e29a444b22d77bbe9e94fece7ea89e6/apps/prairielearn/src/lib/externalGraderCommon.ts), [local execution](https://github.com/PrairieLearn/PrairieLearn/blob/3d750c422e29a444b22d77bbe9e94fece7ea89e6/apps/prairielearn/src/lib/externalGraderLocal.ts), [queue receipt](https://github.com/PrairieLearn/PrairieLearn/blob/3d750c422e29a444b22d77bbe9e94fece7ea89e6/apps/grader-host/src/lib/receiveFromQueue.ts).

The grader contract can convey normalized scores, per-test points, messages, partial results and images, with a documented result-file size bound. The Python result adapter distinguishes student-code exceptions from internal grading errors and supports partial points and skipped follow-on tests. This is richer than treating every unsuccessful process as a failed answer, but its semantics need careful adaptation: UVU's existing integer scoring and all-tests-per-key rule should remain the default. [Python result adapter](https://github.com/PrairieLearn/PrairieLearn/blob/3d750c422e29a444b22d77bbe9e94fece7ea89e6/graders/python/python_autograder/pl_result.py).

Grading jobs record requested, submitted, received, started, finished and graded timestamps, cancellation metadata and result fields. These phases help locate latency in admission, transport, environment startup, execution or result handling. The platform also persists identity-linked variants, answers and submission relationships. That persistence is appropriate to its assessment product, but incompatible with adopting its data model wholesale here. [Grading job table](https://github.com/PrairieLearn/PrairieLearn/blob/3d750c422e29a444b22d77bbe9e94fece7ea89e6/database/tables/grading_jobs.pg).

## Improvements we can incorporate

### Expand validation from a reference solution to a calibration suite

Our seed integrity, reference-model validation and synthetic mutation catalog are already a substantial foundation. PrairieLearn suggests making them one coherent instructor-facing release report: valid solution, known incorrect solutions, invalid bundles and representative variants all carry expected outcomes. A correct model passing proves little about false positives; an intentionally incorrect solution receiving full points is a grader defect.

For each scoring key, curate a small set of synthetic cases and expected point outcomes. Include alternate valid implementations, boundary inputs, wrong types, import failure, infinite loop, missing files and the concept constraints actually taught. Run them through the real Judge0 path, because local pytest alone misses packaging and runtime differences. Persist only instructor-owned fixtures and sanitized validation summaries. Report which requirements have no negative case and which mutations survive. Do not claim that a mutation percentage measures overall pedagogical quality.

### Define a stricter result envelope

Our [parser](../../backend/app/domains/grading/result_parser.py) extracts a JSON object from stdout and uses default values for individual entries. PrairieLearn's named external contract is a useful prompt to formalize ours. Add a protocol version, explicit execution/collection status, stable case IDs, allowed outcomes, bounded diagnostics and an expected-test manifest. Validate before score calculation; recompute scores on the host from trusted configuration.

Unknown markers, duplicate case IDs, missing expected cases, invalid numbers, impossible duration/count fields and unsupported versions should be staff-facing protocol failures. A legitimate empty collection is different from a zero-point student answer. A delimiter helps framing; it does not authenticate output emitted by a process that also runs student code. Stronger typing addresses malformed output, while trusted execution separation addresses deliberate fabrication. Neither should be advertised as solving the other.

### Reproducible variation without persistent student histories

For CS1400/1410, seeded parameterized tests can cover more than one hardcoded example. Start with instructor-authored deterministic case generation during assignment validation. Store generator version, seed and instructor-package identity, and verify that correct models pass every selected seed. Official submissions in a batch should receive a documented comparable case set, not silently changing random difficulty.

Session-local practice variants could be a later feature if an instructor has a clear learning objective. They would need seeds in transient session/run state and exported diagnostics where appropriate. Longitudinal mastery tracking, attempt penalties, per-student difficulty adaptation and exam mode would require a separate product/data decision. They do not follow automatically from adding randomized pytest cases.

### Measure phase latency without collecting submissions

Extend existing [dispatch records](../../backend/app/domains/runs/models.py) and admin monitoring with queue wait, preparation, engine latency, parse/score and cleanup timing. Persistent telemetry should be aggregated by approved operational dimensions, with no student names, code, raw filenames or feedback. Detailed per-submission timelines belong in the transient review workspace. Use bounded histograms rather than unbounded run/session IDs as metric labels.

The immediate purpose is to validate our two-slot host: distinguish long queue waits from slow tests and cleanup failures before increasing concurrency. A latency chart cannot compensate for missing Kata or retention evidence.

## Scope, interoperability and maintenance

PrairieLearn documents Canvas-oriented LTI 1.3 linking and instructor-triggered grade synchronization. The inspected tree also places LTI implementation files under `src/ee`; documented availability should not be assumed to match every self-hosted edition. Its grade-send documentation uses percentage scores scaled by Canvas. That is a useful warning about point conversion and extra credit, not a direct recipe for our current CSV/HTML workflow. [LMS workflow](https://github.com/PrairieLearn/PrairieLearn/blob/3d750c422e29a444b22d77bbe9e94fece7ea89e6/docs/lmsIntegrationInstructor.md).

Do not add AWS queues, object storage, cloud graders, a generalized question-element framework or official AI grading simply because they exist upstream. UVU's current single-host design, anonymous practice and explanation-only AI remain appropriate boundaries. An external grader adapter might eventually ease course-package interchange, but importing arbitrary images/entrypoints would enlarge the trusted instructor and operations surface.

The [root license](https://github.com/PrairieLearn/PrairieLearn/blob/3d750c422e29a444b22d77bbe9e94fece7ea89e6/LICENSE) describes AGPL community content, enterprise-specific content and differently licensed portions, including historical MIT contributions and third-party components. Record the relevant file provenance before considering reuse; this research is not a license interpretation or approval. The monorepo's breadth also means adopting a package can import assumptions about database types, content execution and hosting. The best fit is independently implementing its validation and protocol patterns within our domains.

## Suggested proof of value

Choose three existing synthetic seed packages. Add an author-controlled calibration manifest with at least one passing alternative solution and one deliberately failing case per important scoring requirement. Require consistent results across repeated executions of the same package/seed and show a clean distinction between grader defects and wrong answers. Exercise malformed result data and missing tests without publishing grades. Measure phase timings with the existing 200-submission-plus-sandbox workload before proposing capacity changes. These experiments remain recommendations, not completed validation.
